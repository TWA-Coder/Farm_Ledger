# Web portal

Accounts, configuration, off-chain data and known limits of the web portal (`web/`).

## Signing in

The portal opens on a sign-in page (`web/views/login.js`); the server side is `web/server/auth.js`.

| Who | Signs in with | Acts on-chain as |
|---|---|---|
| **Farmers** | phone number + 4-digit PIN | their **phone account**: an ERC-4337 smart account, the SAME one they use on USSD. Fees are paid by `FarmLedgerPaymaster` |
| **Admin, underwriters, vets, agents** | username + password | their own ordinary account (contract roles are per address, and vets' claim decisions are ECDSA signatures) |

* **Nobody's key is in the browser.** Keys are generated by the server and stored encrypted (AES-256-GCM, key derived from `PHONE_KEY_SECRET`, bound to the address) in `phone_accounts` / `staff_users`. Only the **custody service** (`services/custody.js`) can decrypt them. The browser uses a `RemoteSigner` (`web/lib/remote-signer.js`) that asks `/api/wallet` to send a transaction or sign a message; the portal server checks the session and passes the request to custody.
* **Custody limits what a session can make a key do**: farmers only their own workflow operations (register, record plots and animals, claim, accept or decline offers, pay premiums to FarmLedger); staff only calls to the deployed FarmLedger contracts with no coins attached (each contract then checks the role); messages only in FarmLedger's document-request format; typed data only for the FarmLedger contract.
* **Registration**: name, National ID, phone and farm district, then a 6-digit SMS code and a PIN. The smart account is created and registered on-chain, the farmer joins the district (which assigns their agent) and is signed in. On the local chain, if no SMS provider can reach the number, the page shows the code as a test code.
* **Staff logins** are created by the admin (*Staff logins*: underwriters, vets, admins) or, for agents, by their underwriter (*Agents*). The form creates the login (with a one-time password shown once) and then records the role on-chain from the creator's account: grant the role, certify the vet, or appoint the agent for chosen districts. Admins can reset passwords (new one-time password) and disable logins.
* **Security**: passwords hashed with scrypt; 5 wrong passwords lock a login for 15 minutes; 3 wrong PINs lock the number for 30 minutes on the portal AND on USSD. Sessions are random tokens in an HttpOnly, SameSite=Strict cookie (Secure over https), 12 hours, stored hashed. Changes need an `X-FarmLedger: 1` header, which another site cannot add, against cross-site request forgery.
* **Names** are kept off-chain (`profiles` table) and shown by `/api/names`: staff see everyone's, a farmer sees their own and the staff's.
* Limits: custodial by design (whoever runs the server with `PHONE_KEY_SECRET` can sign for these accounts; the trade-off for farmers without smartphones and staff without wallets). No password reset by email or SMS yet: the admin resets staff passwords; farmers reset their PIN from USSD (option 4). The local bundler does not run the full ERC-7562 validation rules; on a public network use the canonical EntryPoint `0x0000000071727De22E5E9d8BAf0edAc6f37da032` (set `ENTRYPOINT_ADDRESS`).

## Portal configuration (all optional)

| Variable | Default | Purpose |
|---|---|---|
| `RPC_URL` | `rpcUrl` in `web/public/deployment.json` | Chain the portal API reads (vet certification, phone hash) |
| `CUSTODY_URL`, `CUSTODY_TOKEN` | `http://127.0.0.1:4100`, generated (local chain) | How the portal and the phone services reach key custody. Required off the local chain |
| `STAFF_GAS`, `FUNDER_PRIVATE_KEY` | `0.05`, `PRIVATE_KEY` (local: account #0) | Staff accounts are topped up to this much native coin from the funder when they run low |
| `UPLOAD_DIR` | `web/.data/uploads` | Uploaded application and claim documents |
| `FARMLEDGER_DB` | `web/.data/farmledger.db` | Off-chain SQLite database shared by the portal and the services (see *Off-chain data* below) |
| `INDEXER_CONFIRMATIONS`, `INDEXER_CHUNK_BLOCKS` | `0`, `2000` | Event index: blocks to wait before indexing (use ~3 on a public network) and blocks per log request |
| `FARMLEDGER_REVIEWERS` | empty | Comma-separated addresses allowed to view any applicant document (on-chain underwriters can already view them) |
| `BUNDLER_URL` | `http://localhost:4337` | Written into the deployment at deploy time; where the portal sends farmers' UserOperations |
| `BUNDLER_PORT`, `BUNDLER_PRIVATE_KEY` | `4337`, Hardhat account #10 | Bundler service port and the key that submits `handleOps` |
| `PAYMASTER_DEPOSIT_ETH`, `PAYMASTER_MAX_COST_ETH` | `100` (local), `0.05` | Fee sponsorship deposit and the maximum cost of one sponsored operation |
| `DEPLOY_AA`, `ENTRYPOINT_ADDRESS` | off on testnets | Deploy the smart-account contracts on a public network, reusing an existing EntryPoint |

## Off-chain data

One SQLite file (`web/.data/farmledger.db`, git-ignored, owner-only permissions) holds what the chain does not:
plain phone numbers for SMS (`contacts`; the chain stores only their hash), farmers' PINs (`ussd_users`, shared by
USSD and the portal), staff logins with their encrypted keys (`staff_users`), signed-in sessions (`sessions`),
people's names (`profiles`), where
each oracle reading came from (`readings`), and an index of every contract event (`events`). It uses SQLite built
into Node 22.5+, so there is nothing to install. The portal reads activity from `/api/events`, which brings the
index up to date on each request (`web/server/indexer.js`) instead of scanning the chain from block 0. When the local
chain is restarted, the index notices and rebuilds itself.
Older JSON files (`web/.data/contacts.json`, `services/out/ussd-users.json`, `services/out/readings.json`) are
imported once on first start and renamed to `*.imported`.

## Known limits of the test version

* On the local chain the seeded demo logins use Hardhat's public development keys and a shared password (`farmledger`), listed on the sign-in page. On other networks the seed writes one-time passwords and random PINs to `services/out/<network>-logins.txt` instead.
* Test money (`MockRWF`, open faucet). Mobile Money is simulated unless MTN MoMo credentials are set (see [Mobile Money](MOBILE_MONEY.md)); SMS is logged unless an SMS provider is set.
* NDVI is always sample data. CHIRPS is not integrated (NASA POWER rainfall is the real-data option). One oracle key is trusted.
* NAIS contract terms not modelled yet (the 40% government premium share is, see [Premium subsidy](CONTRACTS.md)): excess, cause-of-death and vaccination rules, multi-animal schedules, yield assessment for crops. The policy document states which of these are not applied.
